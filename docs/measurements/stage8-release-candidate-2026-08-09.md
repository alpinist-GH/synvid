- `sbom/cargo-audit-report.txt`, `pip-audit-*.json` — raw scan output.

- `licenses/` — full upstream license texts for the components called out
  below.

**Vulnerabilities: zero, across every ecosystem.** `cargo audit`, `pip-audit`
(both `requirements.lock` and the exact installed venv), `npm audit`, and
`grype` against every generated SBOM all report clean.

**Findings requiring disposition:**
- 17 `cargo audit` "unmaintained"/"unsound" warnings, all against GTK3
  binding crates (`gtk`, `atk`, `gdk`, `glib`, `webkit2gtk`, ...) pulled into
  `Cargo.lock` by `tauri`/`wry`'s Linux backend. Verified with
  `cargo tree --target aarch64-apple-darwin -i <crate>` for each: **none
  resolve for the macOS target** — dead lockfile weight, never compiled into
  this binary. No action needed unless a Linux build target is ever added.
- **Three real GPL-family findings actually shipped in the frozen worker
  bundle**, not just the lockfile:
  1. `phonemizer-fork` 3.3.2 (GPLv3+), imported in-process by `kokoro-onnx`
     for narration phonemization — a Python `import`, which the FSF GPL FAQ
     treats as linking, not mere aggregation.
  2. `libespeak-ng.dylib` (espeak-ng, GPL-3.0-or-later upstream), the native
     library that Python package loads, used by the same narration path.
  3. The bundled `ffmpeg` 7.1 binary (via `imageio-ffmpeg`) reports
     `--enable-gpl --enable-libx264 --enable-libx265` in its own `-version`
     output — a **GPL build, not the LGPL default** — and the worker
     actively selects `libx264` for encoding, so the GPL codecs are in real
     use, not just present. Invoked only via `subprocess` (never linked into
     the worker process), the standard "mere aggregation" case, but GPL
     binary redistribution still requires offering the corresponding source.
  
  **These are license-compliance decisions outside an agent's authority to
  resolve unilaterally** — not fixed this pass. Full detail and concrete
  remediation options (offer FFmpeg source / consider a non-copyleft
  phonemizer path / switch to an LGPL-only FFmpeg build) are in
  `dist/release/THIRD_PARTY_NOTICES.md`. **A real `THIRD_PARTY_NOTICES` file
  still needs to ship inside the `.app` bundle** before any public
  distribution — this pass only produced the dev-tree staging copy.
- Dev-environment leakage check: `strings`/`grep` across the entire frozen
  worker bundle for the developer's home-directory path and Hugging Face
  token patterns (`hf_[A-Za-z0-9]{20,}`) — zero matches.

## 4. Failure-mode tests — two real crash bugs found and fixed

All four found via direct testing against the actual frozen release
artifact (not the dev/source path), using a scratch copy of the signed
`.app` and, for protocol-level cases, a small Python driver talking newline
JSON directly to the frozen `synvid-worker` binary with `SYNVID_APP_SUPPORT`
pointed at a disposable scratch directory (never the real library).

1. **Missing/damaged worker binary → crashed the entire app, not just a
   "worker unavailable" state.** Renaming the bundled `synvid-worker`
   executable out from under a freshly-signed `.app` copy and launching it
   directly hard-aborted the whole Rust/Tauri process before any window
   appeared (`thread 'main' panicked ... panic in a function that cannot
   unwind ... aborting`). Root cause:
   `app/src-tauri/src/lib.rs`'s `.setup()` closure used
   `app.path().resource_dir()?` — `tao`'s native launch-delegate callback
   cannot unwind a Rust panic across its FFI boundary, so any `Err` bubbling
   out of that closure hard-aborts the process instead of the app degrading
   the way `worker_status`'s existing "connected: false" UI path is designed
   to. Fixed by matching on the `Result` instead of `?`-propagating it,
   `eprintln!`-logging any failure, and always returning `Ok(())` so the
   window still opens; the frontend's pre-existing "The local worker is
   unavailable. Reopen SynVid, then try again." messaging (already written,
   just never reachable from this failure) now actually fires. Verified with
   a clean A/B: same fresh signed copy, worker binary removed, before the
   fix crashes every time, after the fix the process survives and the
   window comes up.
2. **Incompatible-newer-schema (and by the same code path, corrupt) SQLite
   metadata → crashed the whole worker process, not a clean per-request
   error.** `worker/store.py` already correctly raises
   `UnsupportedStoreVersion`/`StoreError` for a newer-than-supported
   `PRAGMA user_version` or a failed `quick_check`, but
   `worker/__main__.py`'s main request-dispatch loop's `except` clause
   didn't include `StoreError` in its whitelist, so it propagated out of
   `for line in sys.stdin:` entirely — ending `serve()` and killing the
   worker process out from under Rust mid-session, with no protocol reply
   at all. Reproduced directly: a scratch `index.sqlite3` with
   `PRAGMA user_version = 99` (current schema is 2) made a plain
   `list_outputs` request kill the worker. Fixed by adding a `StoreError`
   handler that replies with a clean `{"code": "store_unavailable", ...}`
   error, then added a further last-resort `except Exception` in the same
   loop as defense-in-depth for the many other synchronous (non-job)
   request kinds that touch the filesystem/store directly (`list_outputs`,
   `story_get`, `recovery_preview`, `model_catalog`, etc.) — job-based
   requests (`generate`, `download_model`, ...) already had this guarantee
   from `JobManager._run`'s own `except BaseException`, this mirrors it for
   the inline dispatch path. Verified against the rebuilt frozen worker:
   the same bad-schema database now returns the clean error and the worker
   stays up to answer a follow-up `get_status` request.

Both fixes are covered by new/existing automated tests
(`diagnostic_tests::*` in `lib.rs` for the diagnostic feature below; the
existing 86-test Python suite still passes unchanged) plus the live
before/after reproduction described above. `cargo build --release` clean.

Also reconfirmed against this frozen release build specifically (behavior
already established in Stages 2 and 7, not new, but worth re-checking on
the actual shipping artifact): `kill -9` on the worker mid-session triggers
Rust's auto-restart within ~2s with a clean UI recovery back to "Ready";
`kill -9` on the outer app leaves no orphan worker process.

**Insufficient disk space and offline model-download failure**: verified by
code review rather than a live destructive test (filling this development
Mac's disk, or toggling its network, was judged too disruptive to risk this
session). `worker/resources.py`'s `ReservationBook.reserve()` raises
`AdmissionError` for insufficient space, and both it and any network
exception during a download or generation job run inside
`JobManager._run`'s `except BaseException` — confirmed by reading the call
sites (`worker/service.py:188,460`) — so both fail as a normal reported job
failure, not a crash. This code path was not exercised live this pass.

## 5. Capability / CSP audit and abuse-case tests

- `app/src-tauri/capabilities/default.json`: a single capability,
  `core:default`, on the one `main` window. No filesystem, shell, dialog, or
  HTTP plugin capability is granted to the webview.
- `Cargo.toml`: no Tauri plugins at all beyond core `tauri` with the
  `protocol-asset` feature (needed for the `asset://` scheme that serves
  generated media). No `tauri-plugin-shell`/`-fs`/`-dialog`.
- 39 `#[tauri::command]`-decorated Rust functions (37 pre-existing + the 2
  new diagnostic commands below), explicitly listed in
  `tauri::generate_handler![...]` — no dynamic/generic command dispatch.
  Native file pickers (`choose_source_image`, `choose_story_*`) go through
  `rfd::FileDialog` directly in Rust, copy into an app-owned root, and
  validate the file (magic-byte check, symlink rejection, size cap) before
  the webview ever sees a path.
- CSP is enforced via a `<meta http-equiv="Content-Security-Policy">` tag in
  `app/src/index.html`:
  `default-src 'self'; connect-src 'self' ipc: http://ipc.localhost; img-src 'self' asset:; media-src 'self' asset:; style-src 'self'; script-src 'self'`
  — no `unsafe-inline`/`unsafe-eval`, no wildcard origins, scoped to Tauri's
  own IPC/asset schemes.
- Path-traversal/symlink/TOCTOU/archive-import-abuse/duplicate-ID/
  decompression-bomb protections for `.synvidstory` import and story-scene
  media replacement were built and tested in Stage 7 (see that stage's
  close-out entry in `PLAN.md`) — not re-derived from scratch here, since
  they're unrelated to packaging and Stage 7 already recorded them
  complete.

## 6. Diagnostic export — built from scratch, was entirely missing

PLAN.md's Stage 8 bullet explicitly requires "an opt-in diagnostic export
whose preview matches its actual bounded contents." Grepping the whole repo
found no such feature anywhere — not in the frontend, Rust, or worker. This
was a real missing deliverable, not an untested one, so it was implemented
this pass:

- `WorkerSupervisor::recent_stderr_lines()` (`app/src-tauri/src/worker.rs`)
  exposes the existing 128-line bounded stderr ring buffer read-only.
- `diagnostic_bundle` (Rust command) assembles app version, OS/arch, worker
  connection state, protocol version, and the redacted stderr tail into one
  string.
- `redact_diagnostic_line` strips the user's home-directory path (→ `~`) and
  any `hf_`-prefixed 20+-char token-shaped string (→ `hf_***redacted***`)
  from every line, covered by three new unit tests
  (`diagnostic_tests::*` in `lib.rs`, all passing).
- `export_diagnostics` takes that exact string back from the frontend and
  writes it verbatim via a native save dialog (symlink-safe atomic
  write-then-hardlink, mirroring `export_video`'s existing pattern) — so the
  saved file **cannot** drift from the previewed text; there's only one
  string, generated once, shown, then written unchanged.
- New "Diagnostics" section in the Settings dialog: opt-in only
  ("Preview diagnostics" button, nothing runs automatically), a read-only
  preview `<textarea>`, then "Export diagnostics…".

Verified end-to-end against the real signed frozen release build: clicked
"Preview diagnostics" (via the accessibility tree, not pixel coordinates —
this Mac's screen was locked for part of this session, which independently
confirmed the app's window/AX behavior is unaffected by that), got a
correct real preview (`app version: 0.1.0`, `os: macos aarch64`,
`worker connected: true`, `worker protocol version: 1`), clicked "Export
diagnostics…", saved through the real native save panel, and confirmed with
`diff`-equivalent byte comparison that the saved file matches the preview
exactly.

## Summary

Real bugs found and fixed this stage, all verified against the actual
frozen, signed release artifact (not just source):
1. DMG build script leaking build-machine absolute paths into the shipped
   image.
2. Missing/damaged worker binary crashing the whole app instead of
   degrading to "worker unavailable."
3. Incompatible/corrupt metadata crashing the whole worker process instead
   of returning one clean per-request error (plus a defense-in-depth
   catch-all for the same class of bug in every other synchronous request
   kind).
4. The diagnostic-export feature Stage 8 explicitly requires didn't exist;
   built and verified it.

**Real gaps still open, not just missing polish:**
- Not notarized (explicit user choice this pass — `notarytool`/hardened
  runtime are ready; this is a deliberate deferral, not a defect).
- No true clean-machine/clean-account install test this pass (explicit user
  choice; Gatekeeper-reject-when-quarantined was verified independently).
- The three GPL-family license findings (`phonemizer-fork`, bundled
  `libespeak-ng.dylib`, GPL-configured bundled `ffmpeg`) need an explicit
  product/legal decision — ship-with-source-offer vs. swap components —
  before any public distribution; not resolved this pass.
- `THIRD_PARTY_NOTICES` exists only in the `dist/release/` dev-tree staging
  area, not yet embedded inside the shipped `.app` bundle.
- Insufficient-disk-space and offline-download-failure were verified by code
  review (the exception-safety mechanism), not by an actual live
  disk-filling or network-disconnection test.
